## R2 客人先进隧道、房主后开房

**前置条件**
- R1 在同一构建下通过；A、B 游戏在跑、Cuprum 已连桥；A 尚未开房。
- A、B 端口输入框留空。

**步骤**
1. A 点「开房」拿到房间码 C，**立刻**把 C 发给 B（A 不等隧道起来）。
2. B 用 C 点「加入」；记录 B 是否短暂出现「等待玩家加入」，以及首次出现「已连接」的时刻；执行 `snap R2-a`。
3. A 端观察连接状态从「等待玩家加入」变「已连接」（房主侧需要 2 个以上 peer）；执行 `snap R2-b`。
4. B **不点任何按钮**（不点「重试」、不重进房间），等连接状态自己变「已连接」；执行 `snap R2-c`。
5. B 点「加入游戏内房间」进同一局；执行 `snap R2-d`。

**预期**
- B 在「等待玩家加入」之后 ≤30 秒自动变「已连接」，全程零手动重试。
- A 端连接状态随后变「已连接」。
- B 游戏内能进 A 的局。

**失败判据**
- B 停在「等待玩家加入」>30 秒，必须点「重试」或重新填房间码才连上。
- B 出现「游戏内控制失败：游戏会话不可用。」等错误并停止自动动作。
- 两端状态互相矛盾（B「已连接」但 A 一直「等待玩家加入」超过 30 秒）。

**证据文件**
- `$EVID/R2-a/`…`$EVID/R2-d/`；`grep -a 'Joining room\|Hosting room' $EVID/R2-d/cuprum-log.txt`。

**原始注入命令**
无注入。严格意义上的「房主后开房」当前做不到：`Hub::start_host` 每次随机生成房间码（`crates/core/src/hub.rs:781`），界面也不提供「按码开房」，因此无法先用某个码让 B 等、再让 A 用同一个码开房。本用例实测的是「B 先进入等待、A 的隧道稍后上线」这一可复现路径。缺口记为 D8，等产品裁决。

```bash
snap R2-a
ss -lunp | grep Casualties
pgrep -af easytier-core
```
