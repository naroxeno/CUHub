## R6 桥断开

**前置条件**
- A 单机；游戏在跑；「游戏内控制」= 已允许；R1 已通过，桥处于已连接状态。
- 记下 Cuhub 的启动命令（恢复时用同一条）。

**步骤（变体 1：先占住 41297 再启动，看 bridge_port_busy）**
1. 退出 Cuhub 与游戏；执行 [commands.md](commands.md) I1 占住 41297；`ss -ltnp | grep 41297` 确认在列。
2. 启动 Cuhub → 启动游戏 → 打开「联机」页：状态栏应出现「桥：端口 41297 被占用」；桥卡提示应是「游戏内桥：…」错误行；执行 `snap R6a-a`。
3. 等 10 秒：确认应用不崩、不反复弹窗、不自动拆隧道；执行 `snap R6a-b`。
4. 释放 I1（Ctrl-C）；≤5 秒桥应自动起来（标志出值），插件连上后会话出现；执行 `snap R6a-c`。插件退避最长 30 秒，等满 30 秒再判失败。
5. 恢复：确认桥与游戏都正常（可在游戏内开房一次）。

**步骤（变体 2：kill Cuhub，看插件重连）**
1. 回到 R1 的正常状态（桥已连、会话在、游戏在跑）；执行 `snap R6b-a`。
2. 执行 [commands.md](commands.md) I3 杀掉 Cuhub（游戏保持运行）；执行 `snap R6b-b`。
3. 用同一条命令重开 Cuhub；≤30 秒观察桥卡标志恢复、会话重新出现；执行 `snap R6b-c`。
4. 恢复：正常退出再启动一次，确认无残留错误。

**预期**
- 变体 1：状态栏原文「桥：端口 41297 被占用」；释放端口后无需重启应用，桥自己起来。
- 变体 2：重开应用后 ≤30 秒恢复会话，游戏不用重启；插件日志出现重连记录。
- 两种变体都不产生崩溃报告。

**失败判据**
- 释放 41297 后 60 秒桥仍未起来，或必须重启应用。
- 必须重启游戏才能恢复会话。
- 应用崩溃（`$CUHUB_DATA/Crash Reports/` 出现新文件）。
- 重开应用后会话一直停在「游戏内桥尚未连接。」>30 秒。
- 插件日志出现 `proto_mismatch` / `bad_token`（版本不匹配，属另一类问题，记入 D 表）。

**证据文件**
- `$EVID/R6a-a/`…`R6a-c/`、`$EVID/R6b-a/`…`R6b-c/`；`grep -a 'CuhubBridge' $EVID/R6b-b/bepinex-tail.txt`；`grep -a 'bridge' $EVID/R6a-a/cuhub-log.txt`。

**原始注入命令**

```bash
# 变体 1：占住桥端口（另一个终端；Ctrl-C 释放）
python3 -c 'import socket,time;s=socket.socket();s.bind(("127.0.0.1",41297));s.listen(1);print("holding tcp 41297",flush=True);time.sleep(900)'
ss -ltnp | grep 41297
# 变体 2：杀桥宿主（= 关 Cuhub），恢复用原启动命令
pkill -f 'cuhub' && sleep 1 && (pgrep -af cuhub || echo "cuhub stopped")
snap R6a-a
```
