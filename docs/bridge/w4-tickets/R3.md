## R3 桥卡片开关（默认关）

**前置条件**
- A 单机；Cuhub 与游戏都已退出（`pgrep -af cuhub`、`pgrep -af Casualties` 空）。
- `Settings.json` 里没有 `dev.cuhub.bridge` 的授权（先执行 [commands.md](commands.md) I5 的「回到默认关」）。
- 记住应用原来的启动方式，后面要重开。

**步骤**
1. 启动 Cuhub 与游戏 → 打开「联机」页；执行 `snap R3-a`。
2. 看桥卡「游戏内控制」行：应为「未允许」，按钮应为「允许」；游戏卡状态应为「尚未允许游戏内控制。」，且**没有**「在游戏内开房」按钮（也没有「加入游戏内房间」按钮）。
3. 点「允许」→ 文案立刻变「已允许」，按钮变「关闭」；不等重启，≤4 秒后游戏卡状态应变「可以开始在游戏内开房。」并出现按钮；执行 `snap R3-b`。
4. 点「在游戏内开房」→ 弹窗「让游戏在 10.144.144.1:<端口> 开房或加入？」→「确认」→ 游戏内开房成功（判据同 R1）；执行 `snap R3-c`。
5. 点「关闭」→ 文案变「未允许」；在游戏内停房（或退出游戏）后重进游戏，等 30 秒观察：Cuhub **不再自动开房**，游戏卡停在「尚未允许游戏内控制。」，活动日志没有新的 `Command mp.host`；执行 `snap R3-d`。
6. 恢复：重新点「允许」，或按 [commands.md](commands.md) I5 用 `Settings.json.w4bak` 覆盖回去。

**预期**
- 关：无开房/加入按钮，状态文案「尚未允许游戏内控制。」，桥卡显示「未允许」。
- 开：≤4 秒（2 个轮询周期）内按钮出现，切回无需重启应用或游戏。
- 关掉后：不再自动下发 mp.host；重新打开后可以再次手动开房。
- 活动日志有且只有对应次数的 `Multiplayer control true for dev.cuhub.bridge.` / `… false …`。

**失败判据**
- 「未允许」时仍渲染「在游戏内开房」按钮，或按钮可点击生效。
- 「允许」后 >10 秒按钮仍不出现，或必须重启应用/游戏才生效。
- 「关闭」后仍下发 mp.host（活动日志出现新的 `Command mp.host`）。
- 切换后设置没落盘：重启 Cuhub 后开关回退到相反状态。

**证据文件**
- `$EVID/R3-a/`…`$EVID/R3-d/`；`grep -a 'Multiplayer control' $EVID/R3-*/cuhub-log.txt`；每拍 `ui-a.png` 必须能看出按钮是否存在。

**原始注入命令**

```bash
# 查看当前授权（应用退出后执行）
cd "$CUHUB_DATA" && grep -A4 'dev.cuhub.bridge' Settings.json || echo "no bridge permissions (default off)"
# 置为默认关 / 置为已允许 / 整体恢复：见 [commands.md](commands.md) I5
snap R3-a
```
