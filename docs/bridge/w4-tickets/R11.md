## R11 房主换端口后的客人侧

**前置条件**
- A、B 两台；R1 已通过；两端「游戏内控制」= 已允许；B 侧处于「已连接」并已在游戏房内。
- A 侧「游戏内控制」= 已允许（房主的端口对账 watcher 只在 Hosting 且控制开启时跑）。

**步骤**
1. 两端各 `snap R11-a`；记录 A 的房间码、当前游戏端口（`ss -lunp | grep Casualties`）、B 的地址行与连接状态。
2. A 在**游戏内**停房 → 地址改 `127.0.0.1:24444` →「启动主机」（不点 Cuprum 按钮）。
3. A 侧 ≤10 秒：活动日志出现 `The game moved to port 24444; room … follows it.`，界面提示「游戏已换到端口 24444。」，房间卡端口行变「端口 24444 · 自动检测」；执行 `snap R11-b`。
4. B 侧 ≤30 秒抓两次（间隔 10 秒）：记录出现的是「房主已离开房间…」还是「房主已换房（游戏端口变了），请用房间码重进。」；执行 `snap R11-c`、`snap R11-d`。
5. 确认 B 停止自动重试（再等 30 秒，`Command mp.join` 计数不增）且地址行不再显示旧端口；执行 `snap R11-e`。
6. B 用**原房间码**重进，端口输入框填 `24444` → ≤60 秒「已连接」，游戏内能进 A 的局；执行 `snap R11-f`。

**预期**
- A 侧对账成功：隧道 hostname/whitelist 跟着变到 24444，界面提示端口已换。
- B 侧出现两条提示之一：优先「房主已换房（游戏端口变了），请用房间码重进。」；若 B 先掉到「等待玩家加入」则可能出现「房主已离开房间，等房主回来后可以重试。」。按代码，B 的 host_drop 只在采到 `Connected{新端口}` 时报「已换房」，否则报「已离开」（`crates/app/src/ui/mp_control.rs:99-111`；隧道 hostname 按客人自己的端口匹配，`crates/core/src/room.rs:151-186`）——所以**哪条先出现就记哪条**，作为本波客人侧的基线；**不要求**两条都出现。
- 两种情况下都必须：自动重试停止、地址行不显示旧端口、B 不崩溃。
- 用原码 + 端口 24444 重进能恢复。

**失败判据**
- B 侧 60 秒内没有任何提示，仍显示「已连接」并往旧端口发包（能连不能玩）。
- B 侧提示出现但自动重试仍在继续，或地址行仍显示旧端口。
- 用原码 + 24444 重进 60 秒内连不上（说明 A 侧白名单/hostname 没跟着换）。
- A 侧出现「游戏端口 24444 不可用：…」或回滚到旧端口（`game_error_game_port` / port_failed）。

**证据文件**
- `$EVID/R11-a/`…`R11-f/`；B 侧重点：`ui-b.png`（提示文案）、`cuprum-log.txt`（`Command mp.join` 计数）、`bepinex-tail.txt`（游戏日志里对 24444 的连接痕迹）。
- A 侧重点：`grep -a 'moved to port\|follows it\|could not follow' cuprum-log.txt`；`easytier.txt`（hostname 应为 cuprum-host-24444）。

**原始注入命令**
无 socket 注入；端口变化在游戏内 UI 做，取证命令：

```bash
ss -lunp | grep -E ':7790|:24444'
pgrep -af easytier-core
grep -a 'moved to port\|follows it\|could not follow' "$CUPRUM_DATA/Logs/"Log*.log | tail -5
snap R11-c
```
