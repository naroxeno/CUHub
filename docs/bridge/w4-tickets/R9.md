## R9 换房 / 重进

**前置条件**
- A、B 两台；R1 已通过（A 在房、B 已进入同一局、两端「已连接」）。
- 两端「游戏内控制」= 已允许。

**步骤**
1. A 执行 `snap R9-a`；记录房间码、隧道端口、`pgrep -af easytier-core` 的输出。
2. A 点「离开房间」→ 确认 → 观察连接状态回「未连接」、房间卡消失；执行 `snap R9-b`，并确认 `pgrep -af easytier-core` 为空、旧端口不再由 EasyTier 持有（`ss -lunp` 里不再出现该端口的 easytr 进程）。
3. A 重新点「开房」→ 得到**新房间码**（这是预期，不是缺陷）→ 把新码发给 B；执行 `snap R9-c`。
4. B 用新码重新加入（端口输入框与 A 端口一致）→ 两端 ≤60 秒「已连接」→ B 进游戏房；执行 `snap R9-d`。
5. 重进场景：A 完全退出 Cuprum（游戏保持运行）再用同一条命令重开；≤30 秒桥恢复、房间卡出现（新码）；B 用新码重进；执行 `snap R9-e`。

**预期**
- 换房后旧隧道被停止：没有残留 `easytier-core` 进程，旧端口释放，旧房间的 peer 列表清空。
- 界面上没有残留错误（连接状态「未连接」而不是「连接已断开」，错误区为空）。
- 新码 60 秒内「已连接」；B 重进后游戏内能进同一局。
- 应用重启后自动重新开房成功，端口与重启前一致。

**失败判据**
- 旧 `easytier-core` 进程残留，或旧端口仍被 EasyTier 占用（会导致下一次开房端口冲突）。
- 换房后界面停在「连接已断开」或错误区残留文案，必须重启应用才清掉。
- 新码 60 秒内连不上，或 B 重进失败。
- 应用重启后不自动开房，或开了两个房间（活动日志两次 `Hosting room` 且只有一个码有效）。

**证据文件**
- `$EVID/R9-a/`…`R9-e/`；其中 `easytier.txt` 用于对比进程残留，`cuprum-log.txt` 用于查 `Hosting room` / `Left the room` 行。

**原始注入命令**
本用例无故障注入；清场核对命令：

```bash
pgrep -af easytier-core || echo "no tunnel"
ss -lunp | grep 7790 || echo "port released"
grep -a 'Hosting room\|Joining room\|Left the room' "$CUPRUM_DATA/Logs/"Log*.log | tail -6
snap R9-b
```
