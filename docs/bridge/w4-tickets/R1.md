## R1 房主先开房、客人后进

**前置条件**
- A、B 完成 [commands.md](commands.md) §1（环境与硬前置）；两端游戏都停在主菜单，未进存档。
- 两端「游戏内控制」= 已允许（未允许时先点「允许」，见 R3）。
- 两端端口输入框留空（A 默认 7790；B 跟随 A）。
- 无残留隧道：两端 `pgrep -af easytier-core` 为空。

**步骤**
1. A 启动游戏到主菜单 → 启动 Cuprum → 展开「联机」页，确认桥卡出现标志（可用 是、运行中 是、服务端/主机 按角色）；执行 `snap R1-a`。
2. A 在「开房」卡点「开房」→ 房间卡出现 6 位房间码，连接状态「等待玩家加入」；执行 `snap R1-b`。
3. A 等游戏卡状态变「可以开始在游戏内开房。」（≤10 秒），再等它自动变「游戏内已开房。」（控制已允许时 ≤10 秒）；执行 `snap R1-c`。
4. B 启动游戏与 Cuprum → 「加入房间」填房间码 → 点「加入」；执行 `snap R1-d`。
5. 两端连接状态变「已连接」（≤60 秒）；B 游戏卡应显示「可以加入游戏内房间。」→ 点「加入游戏内房间」→ 弹窗「让游戏在 … 开房或加入？」点「确认」；执行 `snap R1-e`。
6. 两机进同一局：互相看到角色，走到同一个箱子前开箱，记录是否成功；执行 `snap R1-f`。

**预期**
- 60 秒内两端连接状态都是「已连接」；B 全程没点「重试」。
- A 房间卡地址行 `10.144.144.1:<N>`，游戏卡第二行「房主 · 游戏端口 N（自动检测）」，并且 N 等于 `ss -lunp` 里 Casualties 进程的 UDP 监听端口。
- 活动日志各出现一次 `Command mp.host completed`（A）、`Command mp.join completed`（B），没有重复。
- 游戏内双向可见，开箱有响应（不是「能连上但进不去」，[w4-regression.md](../w4-regression.md) §2.7）。

**失败判据**
- 60 秒后任一端不是「已连接」，或出现「连接已断开」。
- 「已连接」但游戏内看不到对方 / 开箱无响应 / 物品不同步。
- 端口数字与 `ss -lunp` 中游戏进程的 UDP 端口不一致；或游戏已上报端口时来源标签不是「自动检测」。
- 活动日志出现 2 次及以上 `Command mp.host`（重复开房）。
- 界面出现「游戏内控制失败：…」且 30 秒内没有自行恢复。

**证据文件**
- `$EVID/R1-a/` … `$EVID/R1-f/`（每目录含 time.txt、ss-lunp.txt、bepinex-tail.txt、cuprum-log.txt、easytier.txt，另加 ui-a.png/ui-b.png）。
- 关键行：`grep -a 'Command mp\.' $EVID/R1-f/cuprum-log.txt`、`grep -a 'Hosting room\|Joining room' $EVID/R1-f/cuprum-log.txt`。

**原始注入命令**
本用例是基线，不做故障注入；只做清场与取证：

```bash
snap R1-a
pgrep -af easytier-core || echo "no tunnel"
ss -lunp | grep Casualties
```
