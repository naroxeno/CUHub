# core 自查踩坑总结

每轮自查修复后补一条。格式固定：现象 / 根因 / 下次怎么避免。这里只记会再犯的错误，不记一次性的实现细节。

## 1. 门禁把诊断当成了前提

- 现象：用户装好游戏但没装 BepInEx 时，选游戏目录直接报缺失；诊断页本来能显示「未安装」，却进不去。
- 根因：`paths::game_paths` 把 BepInEx 与 Plugins 当硬前提，而 `install::bepinex::detect` 早就能表达「没装、不完整」；两个模块对「什么是有效游戏根」各有一套。
- 下次：校验只限制输入本身的形状（存在、是目录、绝对路径），能力缺失交给诊断与安装流程表达；一个概念只留一处判定。

## 2. 路径包含只做词法，靠调用点补 symlink

- 现象：`is_inside` 只解析 `.`/`..`，父目录指向别处的符号链接能绕过；于是每个写入点又各自查一遍祖先链。
- 根因：照搬上游 `GetFullPath` 的语义，却没意识到写入面比上游大；安全判断被拆成多处，漏一处就破。
- 下次：安全边界函数自己解析到真实路径。修的时候只解析父链、保留叶子——叶子是链接时要能报「不是普通文件」，整体 canonicalize 会把该错误的类型换掉。
- 附带教训：早期测试写死了词法语义，修复时先红后绿，别把旧测试当规格。

## 3. core 长出展示层，与 app 的 i18n 并存

- 现象：`mods.rs`、`metadata.rs`、`modlist.rs` 里有 `*_label` 与 `Display`，app 的 `i18n.rs` 又有一套 `status_detail_key`；同一状态两种文案，其中一套没人调用。
- 根因：先写 core 时顺手给了人读字符串，后来做 i18n 才发现文案该在 app。
- 下次：core 只出枚举与错误码，文案一律在 app；发现没人调用的 label 就是死代码，删掉而不是留着「以后可能用」。

## 4. 原子写各写一遍，多数没有 fsync

- 现象：settings、metadata、modlist、hubconfig、source_choice、nexus_auth、bridge 各有一份 `write_atomic`，有的只 rename，有的连临时文件都没有。
- 根因：每处单独实现，复制时漏掉 `sync_all` 与父目录 sync。
- 下次：写盘只走一个模块（现在 `core::atomic`）；新增落盘点先看有没有现成函数，不要复制。

## 5. 模块名与实职不符

- 现象：`platform/linux.rs` 其实是「非 Windows 实现」，macOS 也走它；`install` 里塞了解包、BepInEx 检测与进程检测；四个模块都叫「来源」。
- 根因：按平台而不是按能力命名，功能增长后名字没跟着改。
- 下次：命名描述能力（`unix`、`process`），不描述平台；一个模块只回答一个问题，装不下就拆，拆之前先问。

## 6. 读取不设上限

- 现象：`dotnet.rs` 直接 `fs::read` 一个 DLL；metadata 缓存直接 `read_to_string`。被换成超大文件时内存直接吃掉。
- 根因：本地文件被默认可信，而网络响应有上限。
- 下次：所有读入内存的入口先看 `metadata().len()`，超限按「不可用」处理；上限常量放模块内并写进文档。

## 7. 渲染期取 Hub 互斥锁

- 现象：远程页渲染时调 `ui.sources_present()`，内部拿 `Arc<Mutex<Hub>>`；目录刷新持锁 20 秒时整页卡住。
- 根因：图省事把「有没有来源表」做成 Hub 查询，没意识到渲染每帧都会调。
- 下次：渲染只读 `Ui` 里的快照 `Signal`，Hub 查询一律在事件回调或 worker 里做。

## 8. 重试没有上限

- 现象：游戏运行时 Apply 每 3 秒重试一次，永远不停；用户关掉弹窗也不知道后台还在转。
- 根因：只写了「等到退出」，没定义放弃条件。
- 下次：任何轮询都要有次数或时长上限，超时给明确提示并结束任务。

## 9. 失败时退化成「看起来能用」的路径

- 现象：`backup_path` 在 `strip_prefix` 失败时 `unwrap_or(target)`，把绝对路径当备份相对路径用。
- 根因：用兜底值掩盖了不该发生的状态。
- 下次：容器约束失败就返回错误（`Outside`），不要造一个能继续跑的替代值。
